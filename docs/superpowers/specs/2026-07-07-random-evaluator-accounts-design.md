# 随机测评用户账号设计

## 背景

管理员端的测评用户页面当前支持批量生成账号。后端会使用部门派生前缀和递增序号生成用户名，例如 `D003-0001`。这种账号格式可预测，并且能明显看出生成顺序。

本次需求是在保留批量生成功能的前提下，让生成的用户名完全随机，同时仍然保证唯一。

## 需求

- 批量生成的测评用户账号必须完全随机。
- 账号不能包含部门 ID、部门编码或递增序号。
- 所有测评用户账号之间必须保持唯一。
- 同一批次内生成的账号在保存前也必须保持唯一。
- 初始密码保持现有行为：6 位大写字母或数字。
- 现有批量生成 UI 和请求结构保持不变：管理员选择部门和生成数量。
- 生成的用户仍然归属于所选部门。

## 账号格式

生成的测评用户账号使用 8 位大写字母或数字，字符集如下：

```text
ABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789
```

示例：

```text
K7P4Q2XA
M9Z0BD4R
```

8 位长度提供足够大的候选空间，同时账号仍然适合打印凭证和手动登录。

## 后端设计

`RandomCredentialGenerator` 负责账号和密码的随机字符串生成。

它会提供随机账号生成能力，每次返回一个 8 位大写字母数字账号。密码生成仍保持 6 位。

`EvaluatorUserService.batchGenerate` 的流程如下：

1. 和现在一样校验管理员权限以及部门是否存在。
2. 持续生成随机账号候选值，直到得到 `count` 个唯一账号。
3. 如果候选账号已出现在当前批次中，则丢弃。
4. 如果 `EvaluatorUserRepository.existsByUsername(candidate)` 返回 true，则丢弃。
5. 使用通过检查的账号和生成的密码，为所选部门创建用户。
6. 保存整批用户，并返回现有响应结构。

为避免极端碰撞场景下出现无限循环，服务层会设置尝试次数上限。一个实用上限是 `count * 20`，并设置最小下限，例如 `100`。如果在上限内无法生成足够数量的唯一账号，则返回业务错误，例如 `生成账号失败，请重试`。

数据库仍通过现有的账号唯一约束作为最终唯一性保障。

## 前端设计

无需修改 UI。表格会自然展示后端返回的随机账号。批量生成弹窗仍然要求选择部门和生成数量，因为账号虽然不再包含部门信息，但生成的用户仍然需要归属到具体部门。

## 错误处理

- 生成数量和部门 ID 的校验错误保持不变。
- 部门不存在时仍返回 `部门不存在`。
- 如果在重试上限内无法生成足够数量的唯一账号，则返回带有明确重试提示的业务错误。
- 如果在预检查之后仍发生数据库唯一约束并发冲突，请求可以通过现有持久化错误处理失败。随机空间和预检查已经让这种情况很低概率；本次范围内不新增分布式锁。

## 测试

后端测试需要更新，覆盖以下内容：

- `RandomCredentialGenerator` 能生成 8 位大写字母数字账号。
- 批量生成返回的账号彼此唯一。
- 生成的账号不匹配旧的部门递增格式。
- 生成的用户仍然使用所选部门。
- 密码仍然是 6 位大写字母数字字符串。
- 现有生成数量最小值和最大值校验测试继续通过。

前端不需要新增行为测试，除非现有快照或断言依赖旧账号格式。
